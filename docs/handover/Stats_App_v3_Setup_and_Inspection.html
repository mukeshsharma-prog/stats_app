This guide takes you from the delivered archive to a running local system, then shows how to submit statistics, read them through the secured API, and inspect RabbitMQ and Keycloak. Archive covered: stats-app-docker-bundle-5505ea7-e2e-v3.tar.gz, packaged on 29 September 2026. Commands below run from the extracted bundle directory unless stated otherwise.

Part 1

What the archive contains

The .tar.gz file is a compressed folder. Extracting it creates the configuration and scripts; Docker then imports the separate stats-app-images.tar image archive. You do not need to extract that inner image archive yourself. Java, Gradle and the source code are not required on the recipient machine.

The archive is approximately 683 MiB and the extracted image archive approximately 689 MiB. Docker's loaded images and persistent volumes need additional space; leave several GB free. The bundle contains seven images: three application images, three infrastructure images, and the Newman test runner. Newman runs temporarily; six containers remain running.

stats-common is a shared library inside application images, not another service. The v3 acceptance path covers lorastats, sysstats and omsstats. The API recognises ltestats and netstats, but their persistence tables and consumers are not implemented in this baseline. An empty API result for them does not prove successful ingestion.

The decision

Six services from one delivered archive

Decision. Keep the six runtime services separate; load the inner image archive through Docker.

Why. The outer tar.gz is a delivery unit, not a combined application process.

Effect. Recipients need Docker and Compose, with no Java or Gradle build. The temporary Newman runner is a seventh image, not a seventh long running service.

Local evaluation boundary: generated configuration uses STATS_INPUT_AUTH_MODE=none. Anyone who can reach port 8081 can submit records. Run on an isolated local machine. The external ingest path has the same local behaviour as the internal path; its name does not add authentication. Keycloak runs in development mode.

Part 2

Prepare extract and start

Step 1 Check prerequisites

Install and start Docker Engine or Docker Desktop with Compose v2. Use Linux or macOS with a terminal, or Windows with Docker Desktop and a WSL shell configured to access Docker. The bundled .sh scripts are shell scripts, not PowerShell commands. Postman Desktop is optional because the included Newman image runs the collection automatically.

docker --version
docker compose version
docker info

The last command must succeed. Ports 5432, 5672, 15672, 8080, 8081, 8082 and 8083 must be free. Existing development containers with names such as stats-postgres also conflict, even if they belong to another Compose project. Use a host compatible with the saved images' platform; an exec format error indicates a platform mismatch.

Step 2 Verify the download and extract it

Place the archive and its supplied .sha256 file together. On Linux or WSL, verify the file before extraction:

sha256sum -c stats-app-docker-bundle-5505ea7-e2e-v3.tar.gz.sha256
tar -xzf stats-app-docker-bundle-5505ea7-e2e-v3.tar.gz
cd stats-app-docker-bundle-5505ea7-e2e-v3

On macOS, use shasum -a 256 -c stats-app-docker-bundle-5505ea7-e2e-v3.tar.gz.sha256 for verification. The expected result is OK. If no checksum file was supplied, request it from the sender. Keep the bundle's folder structure intact because Compose mounts files using relative paths.

Step 3 Start all services

./docker/start-stats-app.sh

The script creates a new .env only if one does not exist, generates random local passwords and a cursor signing key, and restricts the file to its owner. It loads bundled images when any required image tag is missing, runs Compose with project name stats-app-bundle and the apps profile, and waits for the six container health checks. Its total health wait budget is five minutes after Compose starts.

Existing image tags are reused if all seven are already present. When updating from another bundle that uses the same :dev tags, stop the old stack, explicitly load this bundle's images, then start this one:

docker load -i stats-app-images.tar
./docker/start-stats-app.sh

Do not copy the developer's .env into this folder. This bundle generates its own credentials. Preserve that generated file alongside its Docker volumes for subsequent runs; changing its passwords does not automatically change accounts already initialised in PostgreSQL, RabbitMQ or Keycloak.

The decision

Keep credentials matched to retained data

Decision. Reuse the generated bundle .env when restarting retained PostgreSQL and RabbitMQ volumes.

Why. Existing infrastructure does not update initialised account passwords just because a file changes.

Effect. Do not copy a developer .env into the bundle or regenerate passwords while retaining the old accounts.

Step 4 Confirm readiness

docker compose -p stats-app-bundle -f docker/docker-compose.yml --profile apps ps
curl http://localhost:8081/actuator/health/readiness
curl http://localhost:8082/actuator/health/readiness
curl http://localhost:8083/actuator/health/readiness

Expect six running healthy services and "status":"UP" in all three readiness responses. Input depends on RabbitMQ; Writer depends on RabbitMQ and PostgreSQL; API depends on PostgreSQL and Keycloak. Writer applies Flyway migrations and creates partitions during startup. The 7 October service-page update adds browser landing pages at http://localhost:8081/ and http://localhost:8082/, showing the service name, browser port and links to readiness, liveness and metrics. A landing page confirms that HTTP is responding; use readiness to check dependencies. The original v3 and v4 archives predate this update and can return 404 at their root paths.

Part 3

Run the acceptance collection

Option A Run automatically with Newman

./docker/run-postman.sh

This starts a temporary Newman container, injects credentials from the generated .env, uses internal Docker service addresses, and runs the collection with a 500 ms request delay. No manual password copying or separate Newman installation is needed. The bundle includes the runner image, so the default stack and tests can run without registry access after delivery.

Read the final Newman summary. Success means zero failed assertions and exit status zero. The collection sends real records with fresh IDs and current Unix timestamps; it changes local data. It is an acceptance check, not a full production load test. Run it on an otherwise quiet stack: its final assertions require drained main queues and empty DLQs, so residue from previous failure drills can make those checks fail.

Manual verification trap

The two-minute filter moves before every request

The supplied collection script resets fromEpoch to the current time minus 120 seconds and toEpoch to the current time plus 120 seconds on every request. A record submitted more than two minutes earlier can therefore disappear from all three history/list checks while still being readable by UID.

HTTP 200 with "items":[] means no record matched the token's tenant, gateway and time filters. The collection test fails because it expects its sample UID inside that page. Changing an environment time value alone will not fix this: the pre-request script overwrites it.

Use a fixed range when inspecting records after a pause

  1. From Step 6, copy the relevant record's numeric ts.device as T. Use the OMS timestamp for the tenant list, LoRa timestamp for the from-history request and system timestamp for bounded history.
  2. Calculate F = T − 120 and U = T + 120, in seconds. This produces a four-minute bounded range around the stored record and stays within the tenant list's one-hour limit.
  3. In the saved request URL, replace {{fromEpoch}} with the actual integer F and, where present, {{toEpoch}} with the actual integer U. For the tenant-wide query, you can also enter these literal numbers in Params, ensuring there is only one enabled from and one to.
  4. Keep the type, gateway and bearer token as shown below, then select Send. Because the URL now contains literal time values, the collection's changing environment variables cannot move this query range.
  5. Expect the sample UID in items. If still absent, first confirm the UID lookup succeeds, then compare the token tenant and gateway. If the page has other records and a nonnull cursor, follow the next page before concluding the target is absent.

}

Ranges filter ts.device, not the POST time or ts.server. Bounded reads use [from, to): the lower bound is included and the upper bound is excluded. The one-argument device-history route has no upper bound. Tenant lists require both bounds and allow at most one hour; device history does not apply that one-hour cap. Page size defaults to 100 and accepts 1–1000. Results use ts.device DESC, uid DESC.

When nextCursor is nonnull, add cursor=<returned value> in Params and repeat the same URL, time bounds and caller tenant. Continue until it is null. Cursors expire after 15 minutes and cannot be transferred between query shapes or tenants. For literal-time manual checks, retain those literal bounds on every page.

The validated token determines the tenant. A query parameter cannot switch you into another tenant. Foreign or nonexistent UIDs return the same 404; list queries with no visible matches return an empty 200 page. ltestats and netstats are recognised types but have no implemented persistence in this bundle; empty reads for them are not a positive ingestion test.

Step 10 Review the result and repeat safely

  1. For each request, compare its HTTP status and Body with the expectations above, then inspect Test Results. A negative test such as “HTTP 401” should pass when the server correctly refuses access.
  2. Manual Send does not run the next request automatically. In particular, an initial UID-read 404 can defer the polling script's assertion; zero failed tests on that attempt does not prove persistence. Wait for the actual 200 record.
  3. Before returning to Runner, restore any history URLs you changed to literal numbers back to {{fromEpoch}} and {{toEpoch}}, or use an unchanged copy of the imported collection. For one complete automated check, open the collection in Runner, select the same environment, all five folders in order, one iteration and a 500 ms delay. Clear runId before a fresh test set. The final summary should show zero failed assertions.
  4. When inspecting an earlier run, retain its UID variables and use the fixed timestamp procedure in Step 7. Obtain a fresh token if needed. To test a new run, clear runId once, then send the POSTs again before their GETs.
  5. If a test fails, preserve the resolved URL, HTTP status, relevant response body and trace ID. Check time bounds, expected UID and selected tenant before treating an empty page as a storage failure.

This manual sequence is complete when the services are UP, all three callers obtain tokens, the four POSTs are accepted, the three internal records and optional external UID are readable, each list/history query includes the expected record inside its chosen bounds, the six refusal cases behave as specified, and RabbitMQ/Writer evidence is consistent with successful processing.

  5. Open Exchanges and inspect app_stats_input. Its type based routing keys connect records to the corresponding main queues.

The same five names exist with sysstats and omsstats. Retry delays are 30 seconds, 5 minutes and 30 minutes. DLQs intentionally have no TTL or onward route: they preserve the last copy for investigation. Inspect Keycloak in the browser

  1. Open http://localhost:8080/admin/. Sign in using KC_BOOTSTRAP_ADMIN_USERNAME and KC_BOOTSTRAP_ADMIN_PASSWORD. The generated administrator username is admin.
  2. Select realm statsapp, rather than the administrative master realm.
  3. Under Clients, inspect stats-api, stats-input and stats-dev-cli. The development client is used by the Postman token requests.
  4. Under Realm roles, inspect stats.readOnly and stats.ingest. The ingest role exists in the realm but does not enforce access while local Input auth mode is none.
  5. Under Users, inspect the accounts below. Check user attributes, role mappings and the client scopes or protocol mappers that supply the tenant claim and API audience.
AccountInspection purpose

The bundle's realm JSON defines the full setup. API validation expects issuer http://localhost:8080/realms/statsapp, audience stats-api, realm role stats.readOnly and a nonblank string claim named tenant. You can inspect a token locally through Postman's tooling, but do not paste it into a public token decoding website. Logging in to the admin console does not create a Postman reader token.

Realm import runs when the realm does not already exist. Editing the JSON and restarting does not replace an existing realm. Current Compose does not mount a named Keycloak data volume, so removing and recreating the Keycloak container discards its local H2 state and imports the template again. Admin console edits are therefore not a durable deployment configuration. Keep inspection read only unless deliberately changing the local test setup.

Part 7

Stop restart and retain data

./docker/stop-stats-app.sh
# To start again later
./docker/start-stats-app.sh

Stop runs Compose down: PostgreSQL and RabbitMQ named volumes are retained, including PostgreSQL WAL archive storage. Containers are removed. Keycloak local container state is not retained by a named data volume in this bundle, so it is recreated from the realm template on the next start. Keep the generated .env so imported users and retained infrastructure use the same credentials.

To restart one service without removing its container, use:

docker compose -p stats-app-bundle -f docker/docker-compose.yml --profile apps restart stats-writer

Destructive reset only: the following command deletes this project's named volumes, including stored records, queued messages and WAL archives. It is not an ordinary stop command. Save anything you need before using it.

docker compose -p stats-app-bundle -f docker/docker-compose.yml --profile apps down -v

For entirely new random credentials after a deliberate full reset, remove or securely move the old generated .env, then run the start script again. Do not delete that file while retaining data and expect passwords to synchronise automatically.

The decision

A service port does not imply a business API

Decision. Use Input for ingest, API for secured reads, and Writer for readiness and metrics.

Why. Writer owns persistence through message consumption rather than an HTTP write endpoint.

Effect. The Input and Writer landing pages identify the running service and link to operational checks; older bundles can still return 404 at the root. PostgreSQL is not an HTTP service.
