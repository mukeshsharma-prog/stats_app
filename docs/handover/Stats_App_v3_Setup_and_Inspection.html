The Stats App v6

Setup and inspection guide
Run the services and follow all five stat types through the system

Recipient guide · Updated 13 October 2026
Docker Compose · Postman · RabbitMQ · Keycloak · Prometheus

This guide describes the current source and the v6 offline bundle. It covers startup, both ingest paths, all five persisted stat types, secured reads, broker inspection, monitoring and retained data.

Archive covered: stats-app-docker-bundle-v6-prometheus-autostart.tar.gz. Commands run from its extracted directory unless stated otherwise. The startup script, Compose file and 40-request Postman collection match the current source as checked on 12 October 2026.

Version progression

v3 was the three-type delivery with an empty success body. v4 added the JSON ingest acknowledgement; v5 added LTE and network persistence. v6 includes all five types, Input/Writer service pages, automatic Prometheus and PostgreSQL exporter startup, and offline Grafana assets. Use the v6 collection with v6 services.

When upgrading retained volumes, copy the previous deployment’s matching .env into the extracted bundle before startup. The current script always loads the supplied image archive, so reused :dev tags cannot silently select an older build.

stats-common is an embedded library. All five types have consumers, persistence tables and API readers: lorastats, sysstats, omsstats, ltestats and netstats. LTE identifiers follow the current string contract. D-12 P3 was answered on 12 October 2026 (DL-167): the IMSI is stored as received and returned masked on every API route (carrier prefix and, with at least eight subscriber digits, the last four visible), and lac/cid are returned as reported. Supplied network samples do not by themselves close upstream feed confirmation Q15g. Since 13 October (DL-168) Input answers 400 to a record PostgreSQL could never store — an identifier over 128 characters or blank, U+0000, invalid UTF-8, a duplicated member, a ts.server more than an hour ahead — where it used to answer 200 and dead-letter it; a bundle built before that date behaves the old way.

Local evaluation boundary: generated configuration uses STATS_INPUT_AUTH_MODE=none. Anyone who can reach port 8081 can submit records through either path. Keycloak runs in development mode. Use this configuration on an isolated local machine.

Part 2

Prepare, extract and start

Step 1 Check prerequisites

Use Docker Engine or Docker Desktop with Compose v2 and a shell that can run the supplied .sh scripts. On Windows, use WSL configured for Docker access. Postman Desktop is optional.

docker --version
docker compose version
docker info

Docker must be reachable. Ports 5432, 5672, 15672, 8080–8083, 9090 and 9187 must be available; optional Grafana uses 3000. Existing containers with fixed names such as stats-postgres also conflict across Compose projects. Saved images must match the host platform.

Step 2 Verify and extract the archive

Place the archive and checksum file together. On Linux or WSL:

sha256sum -c stats-app-docker-bundle-v6-prometheus-autostart.tar.gz.sha256
tar -xzf stats-app-docker-bundle-v6-prometheus-autostart.tar.gz
cd stats-app-docker-bundle-v6-prometheus-autostart

Expect OK. On macOS use shasum -a 256 -c stats-app-docker-bundle-v6-prometheus-autostart.tar.gz.sha256. Keep the directory structure intact because Compose mounts configuration files using relative paths.

Step 3 Preserve existing credentials, then start

For an upgrade with retained data, copy the previous deployment’s .env into this directory first. For a genuinely new installation, leave it absent so startup generates private random credentials and a cursor signing key.

./docker/start-stats-app.sh

The script refuses to generate new credentials if its PostgreSQL or RabbitMQ volumes already exist. When its existing PostgreSQL container is healthy, it checks both database roles with the supplied credentials before replacing application containers. It always loads a supplied image archive, starts the stats-app-bundle project with the apps profile, waits up to five minutes for eight healthy containers, then checks real successful scrapes for all four monitoring targets and PostgreSQL pg_up=1.

Keep credentials matched to retained data

The source checkout’s stats_app/.env and the extracted bundle’s .env can contain different passwords. Use the file belonging to the running deployment. Changing RABBITMQ_DEFAULT_PASS or POSTGRES_PASSWORD does not update passwords already stored in retained infrastructure. Keep a private backup of the deployment’s file with its data backups.

Step 4 Confirm readiness and monitoring

docker compose -p stats-app-bundle -f docker/docker-compose.yml --profile apps ps
curl http://localhost:8081/actuator/health/readiness
curl http://localhost:8082/actuator/health/readiness
curl http://localhost:8083/actuator/health/readiness
./docker/check-monitoring.sh

Expect eight healthy services, three JSON responses containing "status":"UP", and a monitoring checker result naming Input, Writer, API and PostgreSQL as UP. Input depends on RabbitMQ; Writer on RabbitMQ and PostgreSQL; API on PostgreSQL and Keycloak. Input and Writer root pages identify the service and link to health and metrics. Writer applies Flyway V8/V9 for LTE/network tables and creates retained daily partitions before consumption begins.

Option A Run automatically with Newman

Measured LTE and an etxt-only error are separate shapes. A 2G measurement omits rsrp/rsrq; the error record contains only etxt. Acceptance is the broker handoff

Both paths share StatsIngestController.ingest(). Input checks the envelope, clock skew and limits, publishes received bytes unchanged, and returns acceptance only after a routed confirmation. Invalid payloads can still be rejected by Writer into a DLQ; an expired record can be skipped under retention policy. Use the next steps to prove database persistence.

Time bounds during manual checks: the collection refreshes time variables before every request. After a long pause, the narrow ±120-second window can exclude the earlier record. Read it by UID, take its ts.device, and set literal from/to bounds around that timestamp. Keep a tenant-wide range within one hour. Use the same literal values for every page; restore the original variable URLs before an automated run.

Pages sort by ts.device DESC, uid DESC. Limit defaults to 100 and cannot exceed 1,000. Supply the returned nextCursor as cursor on the same operation, type, filters and caller tenant until null. Signed cursors expire after 15 minutes; changing time bounds or caller invalidates them. Tenant always comes from the validated token. Empty 200 lists and 404 UID lookups can be correct when no record is visible.

Step 10 Review and repeat

  1. Inspect status, Body, Headers and Test Results. An expected refusal such as HTTP 401 should produce a passing negative test.
  2. Require actual 200 readbacks for all stored variants and expected records inside every page.
  3. For a fresh run, clear runId once and send the complete ingest folder before reads. Duplicate requests require the saved primary LTE/network bodies.

If stats / stats does not work

The repository configuration is separate from generated bundle credentials. Identify the running deployment directory without printing its secrets:

docker inspect stats-rabbitmq --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'

The label normally points to the extracted bundle’s docker/ directory; its parent contains the matching .env. Open that file locally. Do not assume a new file overrides the broker’s persisted account. Check account existence and tags with:

docker exec stats-rabbitmq rabbitmqctl list_users

The generated stats user should have the administrator tag. The 12 October troubleshooting check confirmed that the running v6 broker uses the generated bundle password and authenticated successfully through /api/whoami. Passwords are deliberately not embedded in these shareable documents.

Part 6

Inspect Keycloak in the browser

  1. Open http://localhost:8080/admin/. Sign in using KC_BOOTSTRAP_ADMIN_USERNAME and KC_BOOTSTRAP_ADMIN_PASSWORD. The generated administrator username is admin.
  2. Select realm statsapp, rather than the administrative master realm.
  3. Under Clients, inspect stats-api, stats-input and stats-dev-cli. The development client is used by the Postman token requests.
  4. Under Realm roles, inspect stats.readOnly and stats.ingest. The ingest role exists in the realm but does not enforce access while local Input auth mode is none.
  5. Under Users, inspect the accounts below. Check user attributes, role mappings and the client scopes or protocol mappers that supply the tenant claim and API audience.
AccountInspection purpose
alpha-reader / beta-readerReaders for tenant-alpha and tenant-beta; useful for isolation checks

no-tenant / empty-tenantTenant claim absent or unusable; API should return 403

The bundle's realm JSON defines the full setup. API validation expects issuer http://localhost:8080/realms/statsapp, audience stats-api, realm role stats.readOnly and a nonblank string claim named tenant. You can inspect a token locally through Postman's tooling, but do not paste it into a public token decoding website. Logging in to the admin console does not create a Postman reader token.

Realm import runs when the realm does not already exist. Editing the JSON and restarting does not replace an existing realm. Current Compose does not mount a named Keycloak data volume, so removing and recreating the Keycloak container discards its local H2 state and imports the template again. Admin console edits are therefore not a durable deployment configuration. Keep inspection read only unless deliberately changing the local test setup.

Part 8

Stop, restart and retain data

./docker/stop-stats-app.sh
# Start again later from this same bundle directory
./docker/start-stats-app.sh

Ordinary stop removes containers and retains named PostgreSQL, WAL archive, RabbitMQ and Prometheus volumes. Keep the matching .env. Keycloak has no named data volume here, so container recreation reimports its realm template; admin-console edits are not durable deployment configuration.

Restart only Writer without removing its container:

docker compose -p stats-app-bundle -f docker/docker-compose.yml --profile apps restart stats-writer

Deliberate full local reset only: the following deletes this project’s named volumes, including records, queued messages, WAL archives and Prometheus history. Save anything needed first.

docker compose -p stats-app-bundle -f docker/docker-compose.yml --profile apps --profile observability down -v

Generate new random credentials only after a deliberate full reset with all relevant volumes removed. Removing .env while keeping initialised accounts cannot synchronise passwords.

Part 10

Completion checklist

  • Checksum passes and eight default services are healthy.
  • All readiness responses are UP; all four Prometheus targets and pg_up are 1.
  • All five stat types and LTE variants can be accepted and read back with the correct tenant.
  • Collection completes with zero failures; recorded baseline is 40 requests and 99 assertions.
  • RabbitMQ has 25 expected durable quorum queues and five main consumers.
  • Keycloak roles, clients and tenant claims match the local setup.
  • The matching generated .env is retained privately.

Recorded verification and its limits

The 9 October verification report records 2,000 sample readbacks, byte-identical external duplicate replay, all 20 combinations of five types and four read routes, queue topology, and partition bounds/indexes/grants. It records 1,154 regression tests and 117 schema assertions passing. These are dated results, not a new full test run for this document update.

That audit verified partition creation but left live scheduled retention cleanup pending: 30 older LoRa/system/OMS partitions remained and sweep gauges were NaN. Its stated next pass was 10 October, now in the past. Treat cleanup completion as unverified until a newer sweep/partition check confirms it; startup creates partitions but does not perform scheduled cleanup.
